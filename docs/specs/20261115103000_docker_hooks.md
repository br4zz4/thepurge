# what

O thepurge ganha duas features novas, independentes, que estendem a mesma
passada de evicção:

1. **Docker cleanup** — uma fase opcional, dirigida por config, que poda
   imagens dangling e o build cache do builder (`docker image prune -f`,
   `docker builder prune -f`), com opção opt-in de podar imagens não usadas
   (`docker image prune -a -f`).
2. **Hooks** — scripts/comandos do usuário executados ao redor de cada passada:
   `pre_eviction` (antes), `post_eviction` (depois) e `on_failure` (quando a
   passada falha ou não libera nada).

Ambas preservam o modelo de segurança do projeto: dry-run por default (nada
deleta sem `--apply`), config explícita no YAML, e falhas de docker/hook são
avisos, não erros fatais — exceto hook `pre_eviction`, que ao falhar **aborta**
a evicção.

## out of scope

- Volumes, networks e containers parados do Docker (escopo é imagem + build
  cache; `docker system prune` completo fica de fora).
- Hooks por target ou por fase — hooks envolvem a passada inteira.
- Cap de bytes (`max_bytes_per_run`) para a fase docker — prune é um comando
  único, sem cap; os bytes liberados são reportados à parte.
- Flags novas de CLI para docker (`--skip-docker` etc.) — o controle é pelo
  YAML, como decidido.
- Contextos Docker remotos/alternativos — fala-se com o daemon local via
  `docker` do PATH, contexto default.
- Windows — o projeto suporta macOS e Linux; docker/hooks seguem o mesmo
  alcance.
- Hooks em passadas dry-run — dry-run lista, não executa (ver cenários).

## acceptance criteria

### Feature: docker cleanup

```gherkin
Scenario: abaixo do threshold, docker habilitado, dry-run
  Given disco livre abaixo do threshold
  And config com docker.enabled: true, dangling_images: true, builder_cache: true
  And o binário docker existe e o daemon responde
  When roda `thepurge purge`
  Then o output mostra o espaço reclaimable de Images e Build Cache via `docker system df`
  And mostra a lista de imagens dangling
  And nenhum comando de prune é executado
  And nenhuma imagem é removida

Scenario: abaixo do threshold, docker habilitado, apply
  Given disco livre abaixo do threshold
  And docker habilitado no config
  When roda `thepurge purge --apply`
  Then executa `docker image prune -f` (dangling apenas)
  And executa `docker builder prune -f`
  And reporta os bytes liberados pelo docker separadamente dos arquivos evictados

Scenario: unused_images opt-in
  Given config com docker.unused_images: true
  When roda `thepurge purge --apply` abaixo do threshold
  Then executa `docker image prune -a -f` no lugar do prune de dangling

Scenario: sem seção docker no config
  Given config sem a seção `docker` (ou docker.enabled: false)
  When roda `thepurge purge --apply` abaixo do threshold
  Then nenhum comando docker é executado

Scenario: docker ausente no PATH
  Given config com docker habilitado
  And `docker` não existe no PATH
  When roda `thepurge purge --apply`
  Then a passada de arquivos segue normalmente
  And loga warning de docker indisponível
  And a saída não falha por causa disso

Scenario: daemon docker desligado
  Given config com docker habilitado
  And o binário docker existe mas o daemon não responde
  When roda `thepurge purge --apply`
  Then a fase docker é pulada com warning
  And a passada de arquivos segue normalmente

Scenario: evicção de arquivos já resolveu o disco
  Given disco abaixo do threshold
  And a evicção de logs/caches traz o espaço livre de volta acima do threshold
  When roda `thepurge purge --apply`
  Then a fase docker não roda (roda por último, só se ainda estiver abaixo)

Scenario: doctor reporta docker
  Given docker habilitado no config
  When roda `thepurge doctor`
  Then reporta binário docker presente/ausente e daemon alcançável ou não
  And ausência de docker/daemon é aviso e não reprova o doctor
```

### Feature: hooks

```gherkin
Scenario: hooks pre e post em passada apply
  Given config com hooks.pre_eviction e hooks.post_eviction válidos
  When roda `thepurge purge --apply` abaixo do threshold
  Then o hook pre executa antes da evicção
  And o hook post executa depois da evicção
  And os hooks recebem THEPURGE_MODE=apply e THEPURGE_EVENT pre/post conforme o caso

Scenario: hooks rodam mesmo com disco acima do threshold
  Given disco livre acima do threshold
  And config com hooks.pre_eviction e hooks.post_eviction
  When roda `thepurge purge --apply`
  Then os hooks pre e post executam mesmo sem evicção de arquivos

Scenario: pre hook falha aborta a evicção
  Given hook pre_eviction que falha (exit != 0 ou timeout)
  When roda `thepurge purge --apply` abaixo do threshold
  Then a evicção é abortada (nada é deletado)
  And o processo sai com código 1
  And os hooks on_failure disparam

Scenario: post hook falha não aborta
  Given hook post_eviction que falha
  When roda `thepurge purge --apply`
  Then a evicção é mantida e o processo sai com 0
  And a falha é logada e notificada (notify_on_failure)

Scenario: dry-run não executa hooks
  Given config com hooks pre/post
  When roda `thepurge purge` (sem --apply)
  Then nenhum hook executa
  And o output lista "would run" com os hooks

Scenario: hook como comando shell
  Given hook com campo `command` (ex.: "docker compose down")
  When a passada aplica
  Then o comando executa via sh (POSIX) e funciona igual nas duas plataformas

Scenario: hook estoura timeout
  Given hook com timeout_seconds configurado e um script que demora mais
  When a passada aplica
  Then o hook é morto e tratado como falha

Scenario: on_failure quando nada é liberado
  Given disco abaixo do threshold
  And a passada não encontra nada para evictar (0 bytes liberados)
  When roda `thepurge purge --apply`
  Then os hooks on_failure disparam

Scenario: validação de config rejeita hook inválido
  Given hook com `path` e `command` ao mesmo tempo, ou nenhum dos dois
  When roda `thepurge config validate`
  Then falha com erro apontando o hook inválido
```

# why

**Docker:** em máquina de dev, o build cache do Docker é um dos maiores
consumidores silenciosos de disco (frequentemente dezenas de GB em
`~/Library/Containers/com.docker.docker` ou `/var/lib/docker`). O thepurge já
lida com caches e logs; podar imagens dangling e build cache é a mesma
categoria de "lixo regenerável" — seguro de remover, caro de manter. Como o
daemon Docker expõe prune nativo com garantia de não tocar imagens em uso por
containers, delegar ao `docker` CLI é mais seguro e simples que varrer
arquivos do storage driver.

**Hooks:** evicção não vive isolada — o usuário pode querer derrubar algo
antes de limpar (ex.: `docker compose down` para liberar volumes de container
que o prune normal não alcança) ou religar depois. Hooks são o mecanismo
genérico para isso, sem a gente ter que prever cada caso no código.

**Por que dry-run primeiro:** consistente com o resto do projeto — nenhuma
dessas features deleta ou executa nada sem `--apply`; o dry-run mostra o que
faria (reclaimable do docker, lista de hooks).

**Por que pre-hook aborta:** se o usuário declarou um pre hook, é porque a
ordem importa (parar algo antes de mexer). Prosseguir com o pre falho pode
deixar o sistema em estado inconsistente; abortar é o default seguro.

**Por que config-driven (sem flags novas):** o projeto já centraliza o
comportamento no YAML e o serviço reutiliza `run --apply`; docker/hooks como
seções do config funcionam automaticamente no serviço, sem mudar plist/unit.

# how

Todas as tasks seguem o padrão do projeto: código Go 1.x, testes com injeção de
dependências (mesmo padrão de `EngineOptions`), `make test`, `make vet`,
`make fmt` verdes em macOS e Linux (CI já roda os dois + Arch container).

## Task 1 — Config: structs, defaults e validação

**Arquivos:** `config/config.go`, `config/default.go`, `config/default_test.go`,
`config/testdata/config.yml`, `config/config_test.go`.

- Adicionar ao `config/config.go`:

```go
type Docker struct {
    Enabled        bool `yaml:"enabled"`
    DanglingImages bool `yaml:"dangling_images"`
    BuilderCache   bool `yaml:"builder_cache"`
    UnusedImages   bool `yaml:"unused_images"`
}

type Hook struct {
    Path           string `yaml:"path"`
    Command        string `yaml:"command"`
    TimeoutSeconds int    `yaml:"timeout_seconds"`
}

type Hooks struct {
    PreEviction  []Hook `yaml:"pre_eviction"`
    PostEviction []Hook `yaml:"post_eviction"`
    OnFailure    []Hook `yaml:"on_failure"`
}
```

- Campos novos em `Config`: `Docker Docker` (`yaml:"docker"`) e `Hooks Hooks`
  (`yaml:"hooks"`).
- Nova função `Validate(c *Config) error`: cada hook precisa ter **exatamente
  um** de `path`/`command`; `timeout_seconds` negativo é inválido. Reusa
  `ErrInvalidThreshold` onde fizer sentido (threshold já validado no engine).
- `default.go`: default com

```go
Docker: Docker{Enabled: true, DanglingImages: true, BuilderCache: true},
Hooks:  Hooks{},
```

  (`unused_images` fica `false` — opt-in). Seção docker **habilitada** no
  `config init`, como decidido; hooks vazio por default.
- Atualizar fixture `config/testdata/config.yml` com as duas seções e os
  testes de default/marshal para cobrir round-trip.

**Validação:** `make test` (pacote config), `go vet ./config`, `gofmt -l config`.

## Task 2 — `fsutil.ParseBytes` aceita decimais e sufixo "B"

**Arquivos:** `internal/fsutil/bytes.go`, `internal/fsutil/bytes_test.go`.

`docker system df` imprime valores como `12.3MB` e `0B`; o parser atual
(`fmt.Sscanf("%d")`) só aceita inteiros e desconhece o sufixo `B`. Estender
`ParseBytes` para aceitar fração decimal (via `strconv.ParseFloat` com
arredondamento) e o sufixo `B` (multiplicador 1). Manter compatibilidade com
os valores atuais do config (`10GB`, `500`).

**Validação:** `make test` (pacote fsutil), casos novos: `12.3MB`, `0B`,
`1.5GB`, e regressão dos existentes.

## Task 3 — Novo pacote `internal/docker`

**Arquivos:** `internal/docker/docker.go`, `internal/docker/docker_test.go`,
`internal/docker/testdata/fake-docker` (script stub para testes).

- Interface injetável (espelho do padrão `EngineOptions`):

```go
type Ops interface {
    Probe(ctx context.Context) (Status, error)          // OK | BinaryMissing | DaemonDown
    Reclaimable(ctx context.Context) (Reclaimable, error) // Images, BuildCache em bytes
    DanglingImageIDs(ctx context.Context) ([]string, error)
    Prune(ctx context.Context, kind PruneKind) (PruneResult, error)
}
```

- Implementação real `Client` via `exec.CommandContext` com timeout (default
  30s para prune, 5s para probe):
  - `Probe`: `exec.LookPath("docker")` → se ausente, `BinaryMissing`; senão
    `docker version --format {{.Server.Version}}` → erro/timeout = `DaemonDown`.
  - `Reclaimable`: `docker system df --format {{.Type}}\t{{.Reclaimable}}`,
    filtra linhas `Images` e `Build Cache`, converte com `fsutil.ParseBytes`.
  - `DanglingImageIDs`: `docker image ls --filter dangling=true --format {{.ID}}`.
  - `Prune`: `Dangling` → `docker image prune -f`; `AllUnused` →
    `docker image prune -a -f`; `Builder` → `docker builder prune -f`. Lê o
    stdout "Total reclaimed space: X" e converte para bytes.
- `Status`, `Reclaimable`, `PruneKind`, `PruneResult` são tipos do pacote.

**Validação:** testes unitários com `testdata/fake-docker` no PATH (script que
emite saídas fixas conforme subcomando), cobrindo probe ausente/daemon down,
parse de reclaimable decimal e prune; `go vet`, `gofmt`.

## Task 4 — Novo pacote `internal/hooks`

**Arquivos:** `internal/hooks/hooks.go`, `internal/hooks/hooks_test.go`,
`internal/hooks/testdata/*.sh`.

- `type Runner struct { DefaultTimeout time.Duration }` e

```go
func (r Runner) Run(ctx context.Context, event string, mode string,
    hooks []config.Hook) error
```

  - Para cada hook, em ordem: `Path` → executa o arquivo diretamente (exige
    executável; erro de permissão = falha); `Command` → `sh -c "<command>"`
    (POSIX, portável macOS/Linux).
  - Timeout por hook: `TimeoutSeconds` se > 0, senão default 60s — via
    `context.WithTimeout` + `exec.CommandContext`; timeout = falha.
  - Env do hook = env do processo + `THEPURGE_MODE` (`apply`/`dry-run`) e
    `THEPURGE_EVENT` (`pre_eviction`/`post_eviction`/`on_failure`).
  - Falha de um hook não interrompe os demais; a função retorna erro
    agregado (`errors.Join`) com hook e causa.

**Validação:** testes com scripts reais em `testdata` (sucesso, exit != 0,
timeout com `sleep`, checagem de env vars via script que grava num arquivo,
forma `command` via `sh -c`); `go vet`, `gofmt`.

## Task 5 — Fase docker no engine

**Arquivos:** `internal/eviction/engine.go`, `internal/eviction/engine_test.go`.

- `EngineOptions` ganha `Docker docker.Ops` (nil → cliente real criado sob
  demanda quando `cfg.Docker.Enabled`).
- Em `Run`, depois de `DeleteItems` (fora do caminho de early-return acima do
  threshold):
  1. Se `!cfg.Docker.Enabled` ou nenhum recurso ligado (dangling/builder/
     unused) → pula.
  2. Relê o disco (`disk(cfg.Storage.Volume)`); se `free >= threshold` → a
     evicção de arquivos já resolveu; pula a fase docker (não reporta nada).
  3. `Probe`: `BinaryMissing`/`DaemonDown` → registra motivo em
     `res.Docker.SkippedReason`, loga via caller, segue (não é erro).
  4. Dry-run (`!opts.Apply`): preenche `res.Docker.ReclaimableBytes`
     (Images + Build Cache) e `res.Docker.DanglingImageCount`; **não** executa
     prune.
  5. Apply: `Prune(Dangling)` ou `Prune(AllUnused)` conforme `UnusedImages`,
     e `Prune(Builder)`; soma em `res.Docker.FreedBytes`, registra os prunes
     executados em `res.Docker.Prunes`.
- `RunResult` ganha o campo `Docker DockerResult` com `Ran`, `Prunes`,
  `ReclaimableBytes`, `DanglingImageCount`, `FreedBytes`, `SkippedReason`.
  Os bytes docker **não** entram em `FreedBytes` nem no cap
  `max_bytes_per_run` (decisão documentada).

**Validação:** testes de engine com `docker.Ops` fake cobrindo: habilitado +
dry-run (reclaimable reportado, nenhum prune), apply (prunes certos conforme
flags), desabilitado (nenhuma chamada), probe com `BinaryMissing` (skip +
motivo), disco recuperado acima do threshold (fase não roda), ordem
pós-evicção de arquivos. `make test`, `go vet`, `gofmt`.

## Task 6 — Orquestração na CLI: hooks + saída docker

**Arquivos:** `internal/cli/purge.go`, `internal/cli/summary.go`,
`internal/cli/cli_test.go`, `internal/cli/integration_test.go`.

Hooks vivem na CLI (não no engine) porque rodam **mesmo acima do threshold**
(só em apply) — o engine dá early-return nesse caso. Em `runEviction`
(compartilhada por `purge` e `run`):

- Dry-run: imprime `hooks: would run N` listando path/command de cada hook;
  não executa nada.
- Apply:
  1. `hooks.Run(ctx, "pre_eviction", ...)` — erro → `log.Error`, notificação
     (se `notify_on_failure`), roda `on_failure`, retorna exit 1 **sem
     evictar**.
  2. `eviction.Run` — erro → roda `on_failure`, propaga.
  3. `post_eviction` sempre roda (mesmo se o engine errou); falha → log +
     notificação, sem afetar o exit code.
  4. `on_failure` quando: engine retornou erro **ou** passada abaixo do
     threshold sem liberar nada (arquivos + docker = 0). Falha do próprio
     `on_failure` → log, sem recursão.
- Saída docker:
  - dry-run: linha `docker: reclaimable ~X (images) + ~Y (build cache), N dangling image(s)`.
  - apply: `docker freed: Z` separado do `freed:` de arquivos.
- Logging de cada hook (start/fim/exit code) via logger existente.

**Validação:** testes de CLI com hooks fake (script que grava marcador em
arquivo temporário para provar ordem pre→evicção→post), pre-fail aborta (exit
1, nada evictado), post-fail mantém exit 0, on_failure dispara nas duas
condições, dry-run lista sem executar, env vars presentes. `make test`,
`go vet`, `gofmt`.

## desvios registrados

- `docker.Client` também procura o binário em `docker.ExtraPaths` (`/usr/local/bin`, `/opt/homebrew/bin`, `/opt/orbstack/bin`, `/snap/bin`), porque o launchd usa PATH mínimo; plist não mudou.
- Timeout de prune é 5 min (a spec previa 30s); hook em timeout mata o grupo de processos.
- `config.Validate` roda também em `purge`/`run`, não só em `config validate`.
- Evidência: `go vet ./...` limpo, `make fmt` sem diff restante, `go test -count=1 ./...` verde 2x (todos os pacotes `ok`).
